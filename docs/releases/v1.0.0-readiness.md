# Arithvex v1.0.0 — stable-release verification

**Version:** v1.0.0. **Publication rule:** stable release creation is automated and strictly conditional on the successful, separate `.github/workflows/publish-v1.0.0.yml` workflow. Its publication job runs only on a push to `main` that introduces the final release notes file, after both native package jobs and the sanitizer job pass.

## Included components

- C++20 mathematical engine (`ArithvexCore`)
- Native shared mathematical library (`Arithvex`) with legacy C-linkage symbol names
- `ArithvexCLI` interactive console application
- Installed CMake SDK (`find_package(Arithvex CONFIG REQUIRED)`)
- Windows x64 and Linux x86_64 native ZIP distributions, with SHA-256 manifest

## Compatibility and supported platforms

See [v1.0.0 ABI and platform contract](v1.0.0-abi.md). Pre-existing public C linkage names are preserved; the binary DLL/shared-library filename changed. Official binary artifacts cover Windows x64/MSVC and Linux x86_64/GCC only. Other platforms and 32-bit builds are unsupported for v1.0.0. The module named SymbolicCalculus performs numerical calculus; general symbolic algebra is not claimed.

## Release instructions

1. Review PR #11's hardening tests and merge it after all five required checks pass.
2. Review the final stable-version PR, including `CMakeLists.txt`, `README.md`, workflow and [release notes](v1.0.0.md).
3. Merge the final PR to `main` after its checks pass. The `docs/releases/v1.0.0.md` path change triggers the independent stable publication workflow.
4. The workflow builds, installs, executes consumers, packages, verifies both native distributions, and runs ASan/UBSan.
5. Only after the entire pipeline is green does the publisher use GitHub's release CLI to create `v1.0.0` and attach two ZIP files and the combined checksum manifest.
6. Inspect the final GitHub release page and the resulting `main` CI before closing [stable-release issue #9](https://github.com/sanskarIN/Arithvex/issues/9).

If publishing fails due to GitHub Actions token or repository policies, inspect the workflow log and adjust repository settings as authorized; never assert that the release exists merely because the source version changed.
